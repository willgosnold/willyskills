### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Run it with your own tools. Spawn workers with `delegate_task`, each with its whole kickoff in `task`, its own `clientRequestId`, and `mode: "async"`, and keep each returned `taskId` and `childThreadId`. Each completion wakes you, so end the turn instead of waiting. Keep the program's state in its tracker, `notes.md`, and the rest of its store, both under `~/.local/state/pstack/<repo>/`, where `<repo>` is `basename "$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")"` (create it if missing). Also rewrite `$CLAUDE_PROJECT_DIR/.claude/orchestrator-state.md` each time a worker reports, under 6,000 characters. It is the one file that survives compaction, so it lives in the project and not the store. It holds the goal, the path to `notes.md`, the live agents with their `taskId`s, the Pods, the open PRs, the decisions waiting on the user, and the next steps. The compact hook in `references/compact-reload.md` prints it back; install that hook in the project's `.claude/settings.json`, or the file is never read. Watch each PR with `watch_pull_request`, which wakes you on a failed check, required checks passing, a comment or review, or a new conflict. A merge ends the watch without a wake, so keep a `schedule_task` heartbeat while a PR waits to merge. Call no scripts, run no polling loops, and never relay messages or status between agents.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on, pasted in full. Workers can't see their siblings. Run a worker that writes with `isolation: "worktree"`, a checkout of your current local commit. Uncommitted edits are not copied, so commit first or have its kickoff check out a pushed branch. A worker that only reads gets no `isolation` and shares your checkout, with scratch copies in `/tmp`. Every worker runs on this machine, so a runtime check (the project's own verification skill, T3's `preview_*` tools, or the shell for a CLI), transcripts, a simulator, and auth that exists only here work from any worker. Set each subagent's effort for the job, lowering its line's effort for routine work and never raising it, per the Subagents section.
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch.
- **Fork when new work needs a worker's built state,** such as its checkout, uncommitted changes, or a running process. Message a worker only for a follow-up on the same work, with `t3_thread_send` to its `childThreadId`. Never message one to check on it, because a message restarts an idle agent. Read its `task_status` instead, which does not wake it.
- **Each PR gets a verifier that isn't its author,** on the same model and effort as the owner it checks, unless the user named another. The owner merges only on that verifier's pass at the current head.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a control-skill check, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or your forge's equivalents, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Stop it with `task_cancel`, which stops the tasks it delegated too, and confirm with `task_status`. Judge it by its pushes and PR activity, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model after a tool error. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
